# Security Policy

## Supported Versions

This is a personal, open-source utility project. Only the latest version (the `main` branch) is maintained. There is no separate LTS line.

| Version | Supported |
|---|---|
| main (latest) | ✅ Supported |
| Other versions | ❌ Not supported |

## Reporting a Vulnerability

If you find a security issue (e.g. a flaw in the randomness strength, XSS, path traversal, permission issues, etc.), **please do not disclose it in a public issue**. Report it through one of the following private channels:

1. **GitHub Security Advisory private report** (recommended): on the repository page click `Security` → `Report a vulnerability` and fill in the details. The report is only visible to repository maintainers.
2. **Email**: contact the maintainer via the email listed on the GitHub profile (if configured).

Please include the following information to help us triage quickly:

- Vulnerability type and impact scope
- Reproduction steps (minimal if possible)
- Affected endpoints/pages (`/`, `/api/random`, etc.)
- Suggested fix (optional)

The maintainer will confirm receipt within **7 days** and will make a best effort to provide a fix or mitigation within **30 days**. Once fixed, the reporter will be credited in the release notes (if they consent).

## Security Design Notes

### Randomness source

- **Browser**: `window.crypto.getRandomValues` (Web Crypto API, OS cryptographic random source)
- **Server API**: `crypto.randomBytes` (Node.js crypto module)
- The generator uses **rejection sampling** to remove modulo bias, ensuring every character is strictly equally likely

### Privacy

- Generation happens **entirely locally**: strings generated in the frontend make no network requests; the `/api/random` endpoint does not log or store any generated content
- The server does not persist generated data in logs — it only returns results

### Deployment notes

- **Always use HTTPS**: if deployed publicly, configure TLS via a reverse proxy (Caddy / Nginx / Traefik) to prevent strings from being intercepted in plaintext by a man-in-the-middle
- The container already runs as a **non-root user** (see the `USER app` directive in the Dockerfile)
- If no external access is needed, restrict the port to the internal network with a firewall, or bind the container to `127.0.0.1` (`docker run -p 127.0.0.1:3000:3000`)
- The image contains no npm dependencies or package managers, so the attack surface is small; still, periodically `docker pull` to update the base image `node:22-alpine` for security patches

### Usage recommendations (important)

- Strings generated by this tool are suitable for **temporary tokens, test data, session salts**, etc.
- For **real account passwords or long-term keys**, use a dedicated password manager (e.g. Bitwarden, KeePass) or local commands such as `openssl rand -base64 32`, and store them securely
